# PickUpMemo

> 배달 라이더가 배민커넥트에서 **신규 배차를 받는 순간**, 미리 저장해 둔 **가게 메모**와
> **픽업→전달 실제 경로 거리·예상 시간**을 화면 위 **단일 팝업 하나**로 자동으로 띄워주는 Android 앱.
>
> 접근성 서비스 · 시스템 오버레이 · 카카오 지도 API — **실기기에서 동작 검증 완료.**

---

## 1. 왜 만들었는가 (Problem)

배달 라이더는 배민커넥트에서 배차 카드를 받으면 **약 30초 안에 수락/거절을 결정**해야 한다.
그 짧은 시간에 라이더가 알고 싶은 건 두 가지다.

- **"이 가게, 전에 뭐 주의할 게 있었지?"** — 픽업이 까다롭거나, 포장이 늦거나, 주차가 힘든 가게.
- **"여기서 저기까지, 실제로 얼마나 멀지?"** — 직선거리가 아니라 실제 이동 거리·시간.

문제는 이 정보가 **머릿속에만 있거나, 따로 찾아볼 시간이 없다**는 것.
30초 타이머가 도는 배차 화면에서 다른 앱을 열어 검색하는 건 불가능하다.

> 한 줄: *"배차를 받는 그 화면 위에, 판단에 필요한 정보가 자동으로 떠야 한다."*

이건 **실제 배달 라이더로 일하는 지인의 불편을 직접 듣고 시작한 개인용 기술검증 프로젝트**다.

---

## 2. 어떻게 해결했는가 (Solution)

배민커넥트 화면을 **건드리지 않고**(앱 수정 불가) 정보를 얹는 방법은 둘뿐 — 화면을 **읽고**, 그 위에 **그리는** 것.

```
배차 화면 등장
  → 접근성 서비스가 화면 텍스트 수집
  → 상호/주소 인식 (StoreExtractor / AddressExtractor)
  → ① 저장된 메모 매칭   ② 카카오 지도 API로 경로 거리·시간 조회
  → 화면 위 단일 오버레이 팝업 하나에 [메모 + 약 X.Xkm · 약 N분] 통합 표시
```

핵심 설계 원칙은 **"팝업은 절대 하나"**다.
메모용 팝업 따로, 경로용 팝업 따로 띄우면 화면이 어지럽고 실배달을 방해한다. 그래서 메모를 먼저 즉시 띄우고, **느리게 도착하는 경로 정보는 같은 팝업의 한 영역만 비동기로 갱신**하는 구조로 만들었다.

> **버전 흐름**: v2 = 화면 인식 → 메모 매칭 → 팝업. **v3(현재) = 그 팝업 안에 실제 경로 거리·시간 통합.** v3.1 = 오르막 주의(골격만).

---

## 3. 핵심 기능

| 기능 | 설명 |
|------|------|
| **화면 인식 (접근성 서비스)** | 배민커넥트(`com.woowahan.bros`) 단독 대상으로 배차 카드의 "픽업지~전달지" 텍스트 추출 |
| **가게 메모 관리 (CRUD)** | 상호·지점·메모·태그를 Room 로컬 DB에 저장. 상호+지점 포함 매칭 |
| **단일 오버레이 팝업** | 메모 + 경로를 **하나의 팝업**에 통합. 6초 자동 닫힘, 30초 내 중복 팝업 억제 |
| **경로 거리·시간 조회** | 카카오 Local(주소→좌표) + 카카오모빌리티(길찾기)로 `약 X.Xkm · 약 N분` 산출 |
| **debug/release 표시 분기** | 메모도 경로도 없으면 **실배달용(release)은 미표시**, 디버그 빌드만 표시 |
| **수동 테스트 화면** | 배민 앱 없이 픽업/전달지를 직접 입력해 좌표 변환→경로 조회→팝업 전 과정을 재현 |

## 4. 기술적으로 어려웠던 점

1. **30초 안에 도움이 되어야 한다 → 5초 timeout 정책**
   배차 수락 타이머는 약 30초. 경로 조회가 그 안에 안 끝나면 무의미하다. 그래서 geocode+길찾기 전체를 **5초(타이머의 1/6)** 안에 강제 종료(`withTimeoutOrNull`)하고, 초과 시 `거리 정보 확인 불가`로 떨어뜨려 **판단 흐름을 막지 않게** 했다. ANR(앱 멈춤)도 동시에 방지.

2. **비동기 경로 정보와 팝업의 경합**
   메모 팝업은 즉시 뜨고, 경로는 네트워크라 늦게 온다. 그 사이 팝업이 자동으로 닫히거나 새 배차로 교체되면, **늦게 도착한 경로 데이터가 엉뚱한 팝업을 갱신**할 수 있다. `AtomicLong` **토큰 세대**를 발급해, 도착한 갱신의 토큰이 현재 팝업과 다르면 조용히 버리는 방식으로 경합을 막았다.

3. **카카오 자전거 전용 엔드포인트의 불확실성 → 위험 격리**
   조사 결과 카카오의 자전거 전용 길찾기 REST 지원이 불확실했다. 이 불확실성이 코드 전체로 번지지 않도록, **엔드포인트를 `KakaoRouteProvider`의 companion 상수 한 곳에만** 두었다. 미지원이면 그 상수 한 줄만 자동차 길찾기로 바꾸면 되고, 상위 로직은 전혀 손대지 않는다 (Provider 인터페이스로 추상화).

4. **"기존 기능을 절대 깨지 않는다"는 절대 조건**
   v3는 새 앱이 아니라 v2 위의 확장이다. v2의 3대 기능(로그수집·메모 CRUD·메모 팝업)에 회귀가 나면 실패다. 그래서 **수정 파일마다 위험도를 매기고**(高: 팝업 컨트롤러·접근성 서비스), 위험도 높은 파일엔 회귀 검증 항목을 강제했으며, 인식 핵심 모듈(`StoreExtractor`)은 **불변 선언**해 손대지 않았다.

5. **전달지 주소 좌표 변환 실패 → 4단계 fallback**
   배차 화면의 주소는 `****`·괄호 동명 등으로 지저분해 그대로는 좌표 변환이 자주 실패한다. 원문 → 정제 → 도로명 앞부분 → 키워드 검색의 **4단계 fallback**으로 변환 성공률을 끌어올렸다.

## 5. 내가 직접 설계한 부분

> 구현의 상당 부분은 AI 도구가 했지만, **제약을 정의하고 위험을 격리하고 "어디까지 한다"를 정한 것은 나**다.

- **"팝업은 무조건 하나"** — 별도 경로 팝업 컨트롤러 생성을 금지하고 단일 팝업 통합을 강제한 결정.
- **5초 timeout의 근거** — 30초 배차 타이머의 1/6이라는 숫자를 근거와 함께 못박음.
- **위험 격리 패턴** — 불확실한 외부 API(자전거 엔드포인트)를 상수 한 곳에 가두는 설계.
- **debug/release 표시 분기** — 메모·경로 둘 다 없을 때 실배달 방해를 막기 위해 release에선 팝업을 띄우지 않는 정책.
- **회귀 방어 전략** — 수정 파일별 위험도 매트릭스 + `StoreExtractor` 불변 선언.
- **버전 보존 규칙** — 모든 산출물에 `_v3` 표기를 붙여 v2 원본을 무손상 보존, 결정 추적성 확보.

## 6. AI를 어떻게 활용했는가

이 프로젝트의 가장 특이한 점은 **여러 AI 도구를 역할에 따라 분담**시킨 것이다.

- **무거운 판단은 Claude Code(Opus)에 집중** — 설계 단계에서 엔드포인트 위험 격리, timeout 정책, 단일 팝업 통합 구조 등 핵심 의사결정을 처리(설계 토큰 약 109k).
- **명세를 작업 단위(FEAT)로 1:1 분해** — 작업 10개를 "이슈 1개 = 설계 문서 1개"로 쪼개, 각 구현이 그 문서 하나만 보고 가능하도록 만듦.
- **구체화된 구현은 외부 도구(Cursor)에 위임** — 설계가 충분히 구체적인 FEAT-16~23 구현·실기기 테스트는 **인수인계 문서를 계약 삼아 Cursor에 넘김**. Claude Code는 최종 검수만 수행.
- **즉, "설계 품질 = 결과 품질"이라는 전략을 외부 도구 위임으로까지 확장**했다. 무거운 추론은 한 곳에 모으고, 잘 정의된 구현은 어떤 도구가 해도 되도록.

---

## 7. 프로젝트를 통해 배운 점

- **명세가 충분히 구체적이면, 구현은 어떤 AI 도구가 해도 된다.** 핵심은 도구가 아니라 *위임의 계약(인수인계 문서)*의 품질이었다.
- **위험은 없앨 수 없으면 격리한다.** 불확실한 외부 API를 한 줄에 가둔 설계 덕분에, 실기기 테스트에서 문제가 드러났을 때 한 곳만 보면 됐다.
- **기존 기능을 지키는 비용을 설계에 미리 넣어야 한다.** "회귀 금지"를 구호가 아니라 위험도 매트릭스·불변 선언·회귀 검증 항목으로 강제했기에 확장이 안전했다.
- **실사용 문제에서 출발한 기능은 디테일이 다르다.** 30초 타이머, 실배달 방해 최소화 같은 제약은 책상이 아니라 **현직 라이더(지인)의 현장 이야기에서만** 나온다. 사용자를 옆에 두고 만든 것의 강점이다.

## 실행 방법 (요약)

```bash
# JDK 17~21 필요 (기본 JDK가 Java 25면 Kotlin 플러그인과 비호환 → Android Studio 번들 JBR 21 지정)
export JAVA_HOME="/Applications/Android Studio.app/Contents/jbr/Contents/Home"

./gradlew :app:assembleDebug      # 디버그 APK
./gradlew :app:assembleRelease    # 릴리스 APK (미서명)
```

- 산출물: `app/build/outputs/apk/{debug,release}/`
- 카카오 REST 키는 코드에 하드코딩하지 않고 `local.properties`(git 미추적)의 `KAKAO_REST_API_KEY`로 주입한다. **키가 없어도 빌드는 성공**하며, 경로는 `거리 정보 확인 불가`로 처리되고 메모 팝업 등 나머지 기능은 정상 동작한다.
- 설치 후 **OS 설정에서 접근성 + 다른 앱 위에 표시(오버레이) 권한을 수동 허용**해야 팝업이 동작한다(앱 내 안내 제공).
- 클래스·모듈 단위 상세 구현 설명은 [`기술문서.md`](기술문서.md), 전체 설계 근거는 [`03-설계/설계서_v3.md`](../../03-설계/설계서_v3.md) 참조.
